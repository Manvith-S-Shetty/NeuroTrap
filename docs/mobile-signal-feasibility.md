# Mobile Touch Dynamics Signal Feasibility and Architecture Analysis

This document provides a feasibility study, technical investigation, and proposed architecture for smartphone touch dynamics in the NeuroTap project.

---

## 1. Executive Summary

NeuroTap currently implements a machine-learning pipeline and Flutter client based on physical hardware keyboard timing dynamics. This study investigates the feasibility of extending or adapting NeuroTap to capture **smartphone touch dynamics** (touchscreen gestures, tap timing, and touch movement trajectories).

Key findings:
1. **Existing Dataset**: The downloaded PhysioNet neuroQWERTY MIT-CSXPD dataset (`MIT-CS1PD` and `MIT-CS2PD`) contains **only physical hardware keyboard typing records** (`key`, `hold_time`, `release_time`, `press_time`). It contains **zero smartphone touch gesture or spatial coordinate data**.
2. **Flutter Touch Capture Capabilities**: Flutter natively provides high-resolution raw touch event collection across Android and iOS via the `Listener` widget and `PointerEvent` APIs (`PointerDownEvent`, `PointerMoveEvent`, `PointerUpEvent`, `PointerCancelEvent`), yielding microsecond timestamps, $(x, y)$ coordinates, multi-touch pointer IDs, movement deltas, and contact pressure/size metrics.
3. **Model Compatibility**: The current trained NeuroTap model artifact (`LogisticRegression`, $C=100$) relies on **27 physical typing-dynamics features** (`hold_*`, `flight_*`, `inter_key_*`, `key_count`, `recording_duration`, `typing_rate`). Touch features **cannot simply be passed into the current model**. A touch-dynamics model requires an appropriately collected and labeled touch dataset, a dedicated feature extractor, and a separate model training pipeline.
4. **Feasibility Verdict**: Touch dynamics collection on smartphones is **highly feasible from an engine/API perspective**, but requires a separate ML dataset and pipeline.

---

## 2. Current Keyboard Signal

The existing NeuroTap ML pipeline processes 1D timing signals generated by physical keystrokes.

* **Data Model**: Keystroke event sequence $(k_i, t_{\text{press}, i}, t_{\text{release}, i}, \Delta t_{\text{hold}, i})$.
* **Source Signal**: Keystrokes typed on hardware QWERTY keyboards during desktop typing sessions.
* **Extracted Features (27 Features)**:
  * **Hold/Dwell Times**: `hold_mean`, `hold_std`, `hold_variance`, `hold_median`, `hold_min`, `hold_max`, `hold_skewness`, `hold_kurtosis`
  * **Flight Times**: `flight_mean`, `flight_std`, `flight_variance`, `flight_median`, `flight_min`, `flight_max`, `flight_skewness`, `flight_kurtosis`
  * **Inter-Key Latencies**: `inter_key_mean`, `inter_key_std`, `inter_key_variance`, `inter_key_median`, `inter_key_min`, `inter_key_max`, `inter_key_skewness`, `inter_key_kurtosis`
  * **Session Aggregate Counts**: `key_count`, `recording_duration`, `typing_rate`

---

## 3. Hardware Keyboard Feasibility

On mobile devices (Android and iOS), physical hardware keyboards can be connected via Bluetooth or USB-C.

* **Flutter Support**: Supported through `KeyboardListener` and `HardwareKeyboard`.
* **Captured Events**: `KeyDownEvent` and `KeyUpEvent`.
* **Timing Accuracy**: `KeyEvent.timeStamp` provides reliable event ordering and press/release timing.
* **Feasibility**: **Feasible**. Mobile devices connected to physical keyboards can directly feed the existing NeuroTap hardware typing feature pipeline.

---

## 4. Smartphone Software Keyboard Limitation

Normal mobile app interaction uses on-screen software keyboards (virtual soft keyboards).

* **Platform Architecture**: Software keyboards operate through platform Input Method Editors (Android `InputMethodService`, iOS `UIInputViewController`).
* **Flutter Input Model**: Flutter text fields (`TextField`, `EditableText`) interact with soft keyboards via `TextInputClient` and `TextEditingController`.
* **Limitation**: Soft keyboards deliver committed text updates (e.g., via `TextField.onChanged`) rather than raw hardware key-down and key-up events.
* **Missing Timing**: Physical key hold duration (`release_time - press_time`) and flight times between key presses are **not exposed** by standard soft-keyboard text change notifications.
* **Strict Rule**: Press times, release times, and hold durations **must never be fabricated** from `TextField.onChanged` calls. Attempting to approximate physical key timing from text change callbacks generates artificial and invalid data.

---

## 5. Touch Signal Feasibility

Rather than attempting to reconstruct physical key presses from a soft keyboard, smartphone interaction can be measured via **touch dynamics** (raw touchscreen contact events).

* **Concept**: Collecting spatial and temporal dynamics when a user taps, swipes, drags, or gestures across the touchscreen surface.
* **Feasibility**: **High**. Modern capacitive touchscreens on iOS and Android continuously log touch contact state at high sampling rates ($60\text{Hz}$ to $120\text{Hz}+$ digitizer refresh rates).
* **Flutter API Support**: Flutter provides direct access to raw touch events without requiring native C++/Java/Obj-C code.

---

## 6. Candidate Raw Touch Events

Flutter exposes low-level pointer events through the `Listener` widget and `GestureBinding.instance.pointerRouter`.

### Raw Event Types

| Event Type | Flutter Class | Description |
| :--- | :--- | :--- |
| **Touch Down** | `PointerDownEvent` | Triggered when a finger/stylus first contacts the screen surface. |
| **Touch Move** | `PointerMoveEvent` | Triggered continuously as the pointer slides across the screen while maintaining contact. |
| **Touch Up** | `PointerUpEvent` | Triggered when a finger/stylus lifts off the screen surface. |
| **Touch Cancel** | `PointerCancelEvent` | Triggered when a gesture is interrupted by the system (e.g. palm rejection, OS edge gesture). |

### Available Raw Event Properties

* **Timestamps**: `PointerEvent.timeStamp` (`Duration` with microsecond precision relative to system boot/clock epoch).
* **Coordinates**: `PointerEvent.position` (`Offset(x, y)` global logical pixels) and `PointerEvent.localPosition` (widget-relative coordinates).
* **Pointer Identity**: `PointerEvent.pointer` (unique integer ID assigned to an active contact point for multi-touch tracking).
* **Device Characteristics**: `PointerEvent.kind` (`PointerDeviceKind.touch`, `PointerDeviceKind.stylus`, `PointerDeviceKind.mouse`) and `PointerEvent.device` (hardware device identifier).
* **Movement Deltas**: `PointerEvent.delta` (`Offset(dx, dy)` position change since the previous move event).
* **Physical Contact Metrics** (platform dependent):
  * `PointerEvent.pressure`: Touch pressure normalized to $[0.0, 1.0]$.
  * `PointerEvent.size`: Estimated touch surface contact area.
  * `PointerEvent.radiusMajor` / `PointerEvent.radiusMinor`: Elliptical touch contact radius.

### Event Ordering

Touch contact streams follow a strict per-pointer lifecycle:
$$\text{PointerDownEvent} \longrightarrow \big[\text{PointerMoveEvent}\big]^* \longrightarrow \text{PointerUpEvent} \mid \text{PointerCancelEvent}$$

## 7. Candidate Touch Features

From raw touch event sequences, a set of candidate spatial-temporal features can be derived. 

> [!NOTE]
> These candidate features represent exploratory engineering concepts for signal processing and are **not medically validated clinical indicators**.

### 1. Temporal Touch Features
* **Touch Duration (Dwell Time)**: Time elapsed between `PointerDownEvent` and corresponding `PointerUpEvent`:
  $$t_{\text{hold}} = t_{\text{up}} - t_{\text{down}}$$
* **Inter-Touch Interval (Flight/Latency Time)**: Elapsed time between `PointerUpEvent` of gesture $n$ and `PointerDownEvent` of gesture $n+1$:
  $$t_{\text{flight}} = t_{\text{down}, n+1} - t_{\text{up}, n}$$
* **Pause Duration**: Total time within a drag/swipe gesture where instantaneous velocity falls below a minimum threshold ($v < \epsilon$).
* **Tap Frequency**: Total completed tap gestures per unit time during a test session.

### 2. Spatial & Kinematic Features
* **Movement Distance**: Total trajectory path length along `PointerMoveEvent` points:
  $$D_{\text{total}} = \sum_{i=1}^{k} \sqrt{(x_{i} - x_{i-1})^2 + (y_{i} - y_{i-1})^2}$$
* **Net Displacement**: Euclidean distance between touch-down point and touch-up point:
  $$D_{\text{net}} = \sqrt{(x_{\text{up}} - x_{\text{down}})^2 + (y_{\text{up}} - y_{\text{down}})^2}$$
* **Movement Speed**: Average gesture velocity $v_{\text{avg}} = \frac{D_{\text{total}}}{t_{\text{hold}}}$ and instantaneous point-to-point velocities $v_i = \frac{\Delta d_i}{\Delta t_i}$.
* **Speed Variability**: Standard deviation and coefficient of variation of instantaneous speeds within a drag gesture.
* **Acceleration Measures**: Mean and peak absolute acceleration $a_i = \frac{\Delta v_i}{\Delta t_i}$, along with deceleration counts and high-frequency movement tremor/jitter indices.
* **Spatial Dispersion**: Variance of touch-down coordinates $(\sigma_x^2, \sigma_y^2)$ relative to intended target centroids.
* **Straightness Index (Stroke Curvature)**: Ratio of net displacement to total path length ($D_{\text{net}} / D_{\text{total}}$).

## 8. Current Dataset Compatibility

The current downloaded dataset in `ml/data/raw/neuroqwerty-mit-csxpd-dataset-1.0.0/` consists of:
* `MIT-CS1PD`: 62 raw CSV files from 31 participants.
* `MIT-CS2PD`: 54 raw CSV files from 54 participants.

All 116 raw CSV files contain strictly 4 fields per row:
```csv
key, hold_time, release_time, press_time
```

**Verdict**: The current dataset contains **only physical hardware keyboard typing data**. It contains **zero touchscreen gesture data, spatial coordinates, pressure readings, or swipe trajectories**.

## 9. Current Model Compatibility Breakdown

The trained NeuroTap model artifact (`ml/models/neurotap_logistic_regression.joblib`) expects an exact 27-feature input vector:

```text
1.  hold_mean
2.  hold_std
3.  hold_variance
4.  hold_median
5.  hold_min
6.  hold_max
7.  hold_skewness
8.  hold_kurtosis
9.  flight_mean
10. flight_std
11. flight_variance
12. flight_median
13. flight_min
14. flight_max
15. flight_skewness
16. flight_kurtosis
17. inter_key_mean
18. inter_key_std
19. inter_key_variance
20. inter_key_median
21. inter_key_min
22. inter_key_max
23. inter_key_skewness
24. inter_key_kurtosis
25. key_count
26. recording_duration
27. typing_rate
```

### Incompatibility Rationale

1. **Feature Schema Mismatch**: Touch dynamics features (such as spatial coordinates, movement distance, speed variability, gesture acceleration, tap dispersion) do not match the expected 27 typing feature columns.
2. **Domain Mismatch**: `StandardScaler` (`neurotap_standard_scaler.joblib`) was fitted exclusively on desktop keyboard hold/flight timing distributions. Passing spatial movement or touchscreen velocity statistics into this scaler would produce corrupted, meaningless standardizations.
3. **Explicit Rule**: Touch features **CANNOT simply be passed into the current model**.

If touch dynamics becomes a target signal, it requires:
* An appropriately collected and labeled touch dataset (`PD` vs `CNT`).
* A dedicated feature engineering module (`ml/features/touch_feature_extraction.py`).
* A separate model training, hyperparameter tuning, and participant-aware evaluation pipeline.

## 10. Data Requirements for a Touch Model

To train a robust machine-learning model on smartphone touch dynamics, the following data requirements must be satisfied:

1. **High-Resolution Touch Event Logs**: Microsecond-precision timestamps, raw $(x, y)$ position coordinates, pointer IDs, and touch state transitions logged at $\ge 60\text{Hz}$ digitizer sampling.
2. **Standardized Interaction Protocol**: Structured touch tasks (e.g., target tapping grids, point-to-point swiping, or pattern tracing) or controlled soft-keyboard text entry tasks with overlay touch collection.
3. **Clinical Participant Ground Truth**: Recordings paired with participant identifiers (`participant_id`) and ground-truth clinical labels (`PD` vs `CNT`).
4. **Participant-Aware Dataset Partitioning**: Multi-participant cohort with strict participant separation (zero participant overlap across train, dev, and test splits) to prevent data leakage.
5. **Metadata Annotation**: Screen dimension (resolution/DPI), operating system version, and device hardware model to enable cross-device normalization.

---

## 11. Major Technical Risks

1. **Hardware & Digitizer Heterogeneity**: Touch sampling rates vary across smartphone models ($60\text{Hz}$, $90\text{Hz}$, $120\text{Hz}$, $240\text{Hz}$). Touchscreen digitizer sensitivity, screen pixel density (DPI), and OS-level touch smoothing filters differ significantly between Android devices and iOS devices.
2. **System Gesture Interruption**: OS-level edge gestures (e.g., back swipe, home bar swipe, notification drag) produce `PointerCancelEvent`s, interrupting touch trajectories mid-gesture.
3. **Scarcity of Public Clinical Touch Datasets**: Unlike physical desktop QWERTY typing (where benchmark datasets such as neuroQWERTY MIT-CSXPD exist), publicly accessible, clinically validated smartphone touchscreen datasets with Parkinson's ground-truth labels are scarce and often subject to privacy restrictions.
4. **UI Layout & Task Dependence**: Touch dynamics vary depending on button size, screen layout, and whether the user is typing, scrolling, or drawing. Features extracted from one UI task may not generalize to another.

## 12. Recommended Architecture

To maintain pipeline stability while exploring touch dynamics, NeuroTrap should adopt a **Dual-Layer Signal Architecture**.

```text
                              +---------------------------------------------------+
                              |                 NeuroTrap Mobile                  |
                              +---------------------------------------------------+
                                        |                               |
                   Physical Keyboard    |                               | Touchscreen
                   Event Stream         v                               v Event Stream
                              +--------------------+          +--------------------+
                              | Hardware Keyboard  |          | Flutter Listener   |
                              | Collector          |          | Widget Wrapper     |
                              +--------------------+          +--------------------+
                                        |                               |
                                        v                               v
                              +--------------------+          +--------------------+
                              |  TypingEvent List  |          |  TouchEvent List   |
                              +--------------------+          +--------------------+
                                        |                               |
                                        v                               v
+--------------------------------------------------+  +--------------------------------------------------+
|           Hardware Typing ML Pipeline            |  |             Touch Dynamics ML Pipeline           |
| (Existing Implementation)                        |  | (Future Separate Pipeline)                       |
|                                                  |  |                                                  |
| * 27 Keystroke Timing Features                   |  | * Spatial/Kinematic Touch Features               |
| * Saved StandardScaler Artifact                  |  | * Dedicated Touch Scaler                         |
| * Saved Logistic Regression Model                |  | * Dedicated Touch ML Model                       |
| * Participant-Aware Evaluation                   |  | * Separate Touch Evaluation                      |
+--------------------------------------------------+  +--------------------------------------------------+
```

### Flutter Touch Event Collector Architecture (Design Concept)

When touch collection is implemented in Flutter, a non-blocking `Listener` widget should wrap interaction areas:

```dart
// Conceptual Flutter Event Wrapper (Not yet implemented)
Listener(
  onPointerDown: (PointerDownEvent event) => controller.recordTouchDown(event),
  onPointerMove: (PointerMoveEvent event) => controller.recordTouchMove(event),
  onPointerUp: (PointerUpEvent event) => controller.recordTouchUp(event),
  onPointerCancel: (PointerCancelEvent event) => controller.recordTouchCancel(event),
  child: InteractiveTaskWidget(),
)
```

## 13. Next ML/Data Step

1. **Maintain Current Hardware Typing Pipeline**: Keep the existing Python ML pipeline, saved model artifacts, and Flutter hardware keyboard collector intact.
2. **Define Touch Event Schema**: Formalize a standardized JSON/CSV data schema for raw smartphone touch event collection (`pointer_id`, `event_type`, `timestamp_sec`, `x_px`, `y_px`, `delta_x`, `delta_y`, `pressure`, `contact_size`).
3. **Acquire/Collect Labeled Touch Dataset**: Obtain or collect an appropriately labeled smartphone touch dataset containing participant-aware `PD` and `CNT` recordings.
4. **Implement Separate Touch Pipeline**: Build a dedicated touch feature extractor (`ml/features/touch_feature_extraction.py`) and training script (`ml/training/train_touch_model.py`) without modifying the existing typing model or 27 typing features.

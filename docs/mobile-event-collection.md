# Mobile Event Collection

This stage creates the initial Flutter application structure for NeuroTap and implements a controlled typing-session event collector.

It does not implement Flutter ML inference, export the model, modify the Python ML pipeline, modify trained artifacts, or change the final test split.

## Flutter APIs Investigated

The relevant Flutter APIs are:

- `KeyboardListener`
- `HardwareKeyboard`
- `KeyEvent`
- `KeyDownEvent`
- `KeyRepeatEvent`
- `KeyUpEvent`
- `TextField` / `EditableText`

`KeyboardListener` receives callbacks when a user presses or releases a key on a keyboard. Flutter documentation positions it for keyboard and hardware-button events, while text entry itself is handled by `EditableText` and platform input methods.

`HardwareKeyboard` manages key events from hardware keyboards. Its event model includes ordered key tap sequences: `KeyDownEvent`, zero or more `KeyRepeatEvent`s, and `KeyUpEvent`.

`KeyEvent.timeStamp` is a `Duration` relative to an arbitrary start point. The NeuroTap collector converts it to decimal seconds to match the Python event schema.

## Chosen API

The initial collector uses:

```text
KeyboardListener.onKeyEvent
KeyDownEvent
KeyRepeatEvent
KeyUpEvent
KeyEvent.physicalKey
KeyEvent.logicalKey
KeyEvent.character
KeyEvent.timeStamp
```

`KeyDownEvent` starts a pending key press. `KeyUpEvent` finalizes the record:

```text
key = event.character when available, otherwise logicalKey.keyLabel
press_time = KeyDownEvent.timeStamp in seconds
release_time = KeyUpEvent.timeStamp in seconds
hold_time = release_time - press_time
```

`KeyRepeatEvent` is ignored for first-pass hold timing so repeat events do not create extra completed key actions.

Synthesized key events are ignored because they may be generated by Flutter to synchronize state rather than representing a physical key action.

## Session Lifecycle

The app implements:

```text
START
-> clear previous session
-> request keyboard focus
-> begin collecting hardware key events

STOP
-> stop collection
-> clear pending key-down state
-> keep completed events available in memory
```

The screen shows:

- NeuroTap title/header
- short non-diagnostic research/prototype explanation
- text input area
- Start Session button
- Stop Session button
- session status
- captured event count
- development/debug list of captured events

## Event Schema

The Dart `TypingEvent` model corresponds to the Python inference schema:

```text
Dart field      Python field
key             key
pressTime       press_time
releaseTime     release_time
holdTime        hold_time
```

All timing values are decimal seconds.

## Mobile Software Keyboard Limitation

Normal mobile software-keyboard text entry generally flows through text-editing/input-method APIs. `TextField.onChanged` reports text changes; it does not provide reliable physical key-down and key-up events or release timing.

For that reason, this implementation does not fabricate hold or release timings from `TextField.onChanged`.

On Android/iOS with the chosen Flutter API, true key-down/key-up timing is available for hardware keyboard events when Flutter delivers `KeyEvent`s. It cannot be guaranteed for normal on-screen software keyboards through this first-pass implementation.

## What Cannot Currently Be Guaranteed

This first mobile collector cannot guarantee:

- physical press/release timing for normal software keyboard input
- one-to-one mapping to native key events in every platform edge case
- capture of all IME/autocorrect/composition behavior as raw key actions
- production-grade background collection or persistence

The current implementation keeps captured events in memory only.

## Why We Must Not Invent Timings

The trained Python pipeline expects:

```text
key
hold_time
press_time
release_time
```

Inventing `release_time` or `hold_time` from text-change callbacks would create data with different semantics from the research dataset and the Python inference pipeline. That would make downstream features misleading.

## Next Integration Step

Flutter integration with the Python-derived inference artifact is intentionally not implemented here.

A later stage can decide how to reproduce the exact 27-feature extraction and saved scaler/model behavior on device. This stage only establishes the event/session collection boundary.

## Safety Boundary

NeuroTap is a non-diagnostic research/prototype screening system. This mobile screen collects typing dynamics for engineering experimentation and does not show a medical or diagnostic result.
